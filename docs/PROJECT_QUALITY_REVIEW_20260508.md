## 二、技术架构评估

### 2.1 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    前端 (React + Vite)                    │
│  Ant Design 5 · Tiptap Editor · Zustand · TanStack Query │
└────────────────────────┬────────────────────────────────┘
                         │ REST API / SSE
┌────────────────────────▼────────────────────────────────┐
│                  后端 (Flask, 端口 3012)                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│  │ API 路由  │  │  AI 服务  │  │ RAG 检索  │  │ 文档导出  │ │
│  │ routes.py │  │ qwen_cli │  │ retrieval │  │ md_to_wd │ │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘ │
│  ┌──────────────────────────────────────────────────────┐ │
│  │          数据访问层 (supabase_repo.py)                │ │
│  └──────────────────────────────────────────────────────┘ │
└────────┬───────────────────────────────┬─────────────────┘
         │                               │
    ┌────▼────┐                    ┌──────▼──────┐
    │ SQLite  │                    │  Supabase   │
    │ (本地)   │                    │ (PostgreSQL │
    │         │                    │  + Storage) │
    └─────────┘                    └─────────────┘
```

### 2.2 技术栈评价

| 层级 | 选型 | 评价 |
|------|------|------|
| 后端框架 | Flask | 轻量适合 MVP，但缺少 ORM、中间件、依赖注入等生产级特性 |
| 前端框架 | React 18 + Vite + TypeScript | 主流选型，类型安全，构建快 |
| 状态管理 | Zustand | 轻量合适，避免 Redux 的过度工程 |
| 数据获取 | TanStack Query + Axios | 支持缓存、轮询、乐观更新，选型优秀 |
| UI 组件 | Ant Design 5 | 企业级组件库，表单/表格/步骤条等组件齐全 |
| 富文本 | Tiptap | 扩展性强，适合标书编辑场景 |
| AI/LLM | DashScope (通义千问) | 国内合规，支持流式，成本可控 |
| 向量库 | ChromaDB + pgvector | 双轨架构，本地/云端灵活切换 |
| 数据库 | SQLite + Supabase | 双数据源增加复杂度，建议统一 |

### 2.3 架构亮点

1. **AI + 规则双路径大纲生成**: 规则引擎快速兜底，LLM 异步复核优化，兼顾速度和质量
2. **SSE 流式输出**: 大纲生成和章节编写均支持实时推送，用户体验流畅
3. **任务状态机设计**: `bid_generation_tasks` 表实现了 queued → running → done/failed/stopped 状态流转，支持刷新恢复
4. **三层 RAG 检索管线**: 向量召回 → 关键词补充 → Rerank 重排序，召回质量有保障
5. **DOCX 导出任务化**: 异步队列 + 轮询，避免大文件导出阻塞请求

### 2.4 架构风险

| 风险项 | 严重度 | 说明 |
|--------|:------:|------|
| 双数据源混用 | 中 | SQLite + Supabase fallback 逻辑增加维护成本和数据一致性风险 |
| 无独立任务队列 | 中 | 线程池 + 前端轮询模式在高并发下不可靠，进程重启丢失任务 |
| 路由层过重 | 中 | `routes.py` 900+ 行混合业务逻辑，违反单一职责 |
| 全局内存状态 | 低 | `temp_analysis_store` 无过期清理，存在内存泄漏风险 |
| 无服务端渲染/SSR | 低 | 纯 SPA 部署，SEO 和首屏性能非核心关注点 |

## 三、业务闭环评估

### 3.1 核心业务流程完成度

```
上传招标文件 ──→ 文档解析 ──→ AI 结构化解读 ──→ 章节大纲 ──→ 正文生成
     ✅            ✅            ✅              ✅          ✅

──→ 合规检查 ──→ 在线编辑 ──→ Word 导出 ──→ ONLYOFFICE 终稿
     ⚠️            ✅           ✅            ✅
```

| 环节 | 状态 | 详细说明 |
|------|:----:|----------|
| 文件上传 | ✅ 完成 | 支持 Word/PDF/TXT，SHA-256 去重，Supabase Storage 持久化 |
| 文档解析 | ✅ 完成 | 原生解析 + MinerU OCR 双通道，200 页以上自动分片 |
| AI 解读 | ✅ 完成 | 提取项目概况、资格要求、评分标准、废标风险、时间节点 |
| 章节大纲 | ✅ 完成 | 规则引擎秒出 + LLM 异步优化，支持分册（技术标/商务标/资格/报价） |
| 正文生成 | ✅ 完成 | 注入企业画像 + RAG 知识资产 + 写作策略，流式输出，失败保稿 |
| 合规检查 | ⚠️ 基础版 | 规则匹配完成，LLM 语义复核（P3）未实现 |
| 在线编辑 | ✅ 完成 | Tiptap 富文本，支持标题/表格/列表，实时脏状态检测 |
| Word 导出 | ✅ 完成 | 中文排版规范（宋体/黑体），自动处理表格/图片/Mermaid 图 |
| ONLYOFFICE | ✅ 完成 | Docker 部署，JWT 认证，支持在线协同终稿编辑 |
| 用量统计 | ✅ 完成 | Token 计量 + 成本估算 + 按操作/阶段聚合 |

### 3.2 业务缺口

| 缺口 | 优先级 | 影响 |
|------|:------:|------|
| 合规检查未升级为 LLM 语义复核 | P3 | 无法识别语义层面的遗漏，仅做关键词匹配 |
| RAG 未按分册加权召回 | P2 | 技术标/商务标/资信混召回，影响正文相关性 |
| 分册维度合规覆盖率未实现 | P2 | 工作台仪表盘缺少分册粒度的质量指标 |
| 历史记录无分册进度 | P3 | 用户无法回溯某分册的完成状态 |
| 正式 `bid_volumes` 表未建立 | P3 | 分册定义依赖 metadata 过渡方案 |
| 无标书版本管理 | P3 | 无法对比不同版本的标书差异 |

## 五、安全评估

### 5.1 已实施的安全措施

| 措施 | 说明 |
|------|------|
| 请求体大小限制 | 防止大 payload 攻击 |
| 响应脱敏 | 500+ 错误自动替换敏感信息为 `***` |
| 文件上传白名单 | 扩展名 + MIME 双重校验 |
| SQL 注入防护 | Supabase 链式查询构建器，无 SQL 拼接 |
| CORS 配置 | Flask-CORS 跨域控制 |
| 环境变量管理 | .env + .env.example 分离 |
| Supabase 写重试 | 3 次指数退避重试 |
| AI 限流处理 | 429 状态码特化提示和重试 |

### 5.2 安全风险

| 风险 | 严重度 | 说明 | 建议 |
|------|:------:|------|------|
| 无强制认证 | 高 | `APP_AUTH_ENABLED` 默认关闭，浏览器指纹可伪造 | 生产环境必须启用 Token 认证 |
| SSRF 风险 | 中 | DOCX 导出下载图片未校验目标地址 | 添加 URL 白名单或禁止内网地址 |
| JWT Secret 弱 | 中 | `ONLYOFFICE_JWT_SECRET` 默认空字符串 | 启动时强校验非空 |
| 错误信息泄漏 | 低 | `APP_EXPOSE_DEBUG_ERRORS` 可暴露堆栈 | 生产环境强制关闭 |
| 并发文件冲突 | 低 | Mermaid config.json 并发写入覆盖 | 使用 tempfile 替代固定路径 |

## 七、改进建议（按优先级排序）

### 7.1 短期（1-2 周）

1. **抽取 Service 层**: 将 `routes.py` 中的业务逻辑下沉到 `backend/services/`，路由层仅做参数校验和响应封装
2. **统一错误处理**: 定义项目级异常类，替代宽泛 `except Exception`，统一错误响应格式
3. **补全基础测试**: 为 AI 模块、RAG 检索、文档导出编写核心路径单元测试
4. **添加 Lint 配置**: Python 用 Ruff，前端用 ESLint + Prettier，统一代码风格

### 7.2 中期（2-4 周）

5. **Docker 容器化**: 编写 Dockerfile + docker-compose，实现一键部署
6. **CI/CD 流水线**: GitHub Actions 或 GitLab CI，自动运行 lint + test + build
7. **SSRF 防护**: 图片下载添加目标地址校验，禁止内网/回环地址
8. **认证鉴权**: 生产环境强制启用 Token 认证，添加中间件级身份校验
9. **supabase_repo 拆分**: 按领域拆分为 `usage_repo.py`、`section_repo.py`、`knowledge_repo.py`

### 7.3 长期（1-2 月）

10. **LLM 语义合规检查**: 实现响应证据摘录和置信度评分
11. **分册 RAG 联动**: 按分册类型加权召回知识资产
12. **水利行业数据扩充**: 补充泵站、河道治理、堤防等高频子类样本
13. **独立任务队列**: 引入 Celery 或 Redis Queue 替代线程池 + 轮询
14. **标书版本管理**: 支持版本对比和回滚

## 八、结论

本项目作为**水利行业单企业自动化标书编制 MVP**，已达到**可演示、可试用**的阶段：

- **核心业务链路完整**: 从招标文件上传到 Word 导出的 8 个关键环节全部打通
- **AI 工程质量较高**: Prompt 结构化程度、幻觉抑制策略、分册写作策略在同类项目中属上乘
- **前端体验流畅**: 5 步工作流 + 质量仪表盘 + 断点恢复，用户学习成本低
- **文档体系完备**: README 和专题文档可支撑新人快速上手

主要差距集中在**工程化基础**（零测试、无 CI/CD、无容器化）和**业务深度**（合规语义检查、分册联动、行业数据广度）。这些差距在 MVP 阶段可以接受，但应在产品化前系统性补齐。

**总体判断**: MVP 阶段完成度约 **70%**，核心功能闭环，工程化和行业深度有明确改进路径，具备产品化推进的基础。
